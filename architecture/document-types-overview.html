Multi-Format Document Architecture

Summary

AgentDocs now accepts HTML and Markdown through a renderer registry while continuing to serve every document as a committed index.html. Original source is preserved beside the rendered artifact, so future renderers can be added without changing the web UI, search index, historical viewer, or docs origin. Invalid document input is rejected before filesystem or Git mutation with a specific 4xx response.

Context

The Markdown contract follows the Markdown Guide basic syntax and its extended syntax; that guide notes that extended features are processor-specific, so AgentDocs defines an explicit dialect below.

Evaluations

Size 1
One server pipeline, CLI MIME selection, tests, and documentation changed.
Complexity 2
Format dispatch, deterministic storage, Markdown dialect coverage, and input failure semantics interact.
Risk 1
The universal index.html contract keeps existing viewers and legacy vaults compatible.

Locked Decisions

D1 — Universal web artifact. The docs origin remains deliberately format-blind and only serves index.html, including historical Git revisions.
D2 — Explicit Markdown dialect. “Extended” means every feature listed in the Markdown Guide feature matrix under Anything Else, not an ambiguous promise of whichever defaults a library happens to enable.
D3 — Client input errors stay client errors. Malformed multipart is 400, unsupported formats are 415, and invalid source or renderer failures are 422; genuine Git/filesystem failures remain 500.

Open Decisions

D6 — Custom renderer discovery

A. Compile-time registry

Add a DocumentRenderer object to application composition. Smallest attack surface and simplest deployment; adding a renderer requires a release.

B. Configured JavaScript modules

Load renderer packages named in configuration. Fast extension, but arbitrary modules execute with full server privileges and complicate failure isolation.

C. Subprocess protocol

Send source to external renderer commands and accept HTML back. Language-neutral and isolatable, but introduces process lifecycle, timeout, and deployment complexity.

Opinion

Keep A for now. The registry already makes renderer code local and testable; move to C only when a concrete non-JavaScript DSL needs independent deployment, and avoid B unless the vault is explicitly treated as a trusted-code plugin host.

Plan

  1. Introduce a renderer interface and registry → verify HTML pass-through and injected custom renderers.
  2. Add the Markdown renderer and explicit syntax plugins → verify every dialect feature in one focused unit suite.
  3. Render before persistence and retain source/type metadata → verify failed uploads create no files, commit, or index row.
  4. Keep index.html as the read model → verify latest, historical, search, and reindex flows for both formats.
